MAX LLM

1.1 Run and serve an LLM

In this section you run a real language model with MAX four ways, from three lines of Python to an OpenAI-compatible server:

  1. AutoPipeline: text in, text out.
  2. AutoTokenizer and AutoModel: the tokens and scores underneath.
  3. max generate: the same thing from the command line, with timings.
  4. max serve: an HTTP server that any OpenAI client can call.

The model is SmolLM2-135M-Instruct, a 135M-parameter chat model from Hugging Face. It is small enough to run anywhere, and its architecture (the Llama family) is the one most open models use. The rest of the book rebuilds it from scratch.

If you are new to LLM inference, read What is LLM inference? in the Modular handbook first.

Setup

MAX runs on a GPU if it finds one, otherwise on the CPU. Every call below asks for float32 numbers. MAX requires float32 on a CPU, since it runs bfloat16 weights only on GPUs; on a GPU, float32 keeps the results comparable with the rest of the book. The first run downloads the model (about 270 MB) and compiles it, which takes a minute; later runs reuse both caches.

import logging
import subprocess
import time
import urllib.request

import numpy as np
import plotly.graph_objects as go
from max.pipelines import AutoPipeline
from openai import OpenAI

from minillm import viz

# MAX logs performance hints that don't matter at this model size.
logging.getLogger("max").setLevel(logging.ERROR)

MODEL = "HuggingFaceTB/SmolLM2-135M-Instruct"
FLOAT32 = dict(quantization_encoding="float32")

Generate text in three lines

AutoPipeline loads a model and its tokenizer and generates text, much like transformers.pipeline. top_k=1 makes generation greedy: it always picks the most likely next token, so the output is the same on every run.

pipe = AutoPipeline(MODEL, **FLOAT32)
completion = pipe(["The capital of France is"], max_new_tokens=16, top_k=1)
assert "Paris" in completion[0]
completion

['The capital of France is Paris. Paris is the largest city in France and the capital of the French department']

A plain string goes to the model as is, and the output starts with the prompt. An instruct model is trained on conversations, so a list of chat messages usually works better. The pipeline formats them with the model’s chat template and returns only the reply.

messages = [{"role": "user", "content": "What is the capital of France?"}]
pipe([messages], max_new_tokens=32, top_k=1)

['The capital of France is Paris.']

Look underneath: tokens and scores

A language model doesn’t read text. A tokenizer splits the text into tokens (whole words, pieces of words, or punctuation) and maps each to an integer ID. SmolLM2’s vocabulary has 49,152 tokens.

tokenizer = pipe.tokenizer
ids = tokenizer(["The capital of France is"])["input_ids"][0]
print(ids)
viz.tokens([tokenizer.decode([i]) for i in ids], ids)
The·capital·of·France·is
[504, 3575, 282, 4649, 314]

Each chip is one token; hover over it for its ID, and the dots mark spaces. Common words are single tokens, usually with their leading space. Rare words, numbers, and code split into pieces:

text = (
    "Tokenizers split unbelievably rare words, 3.14159, and snake_case_names."
)
pieces = tokenizer([text])["input_ids"][0]
viz.tokens([tokenizer.decode([i]) for i in pieces], pieces)
Tokenizers·split·unbelievably·rare·words,·3.14159,·and·snake_case_names.

Given the IDs, the model produces one score (a logit) for every token in the vocabulary: its prediction of what comes next. AutoModel.generate can return those scores. Softmax turns them into probabilities: it exponentiates each logit \(z_i\) and divides by the total, so every probability is positive and they sum to 1:

\[p_i = \frac{e^{z_i}}{\sum_j e^{z_j}}\]

model = pipe.model
out = model.generate(input_ids=[ids], max_new_tokens=1, output_logits=True)

logits = out.logits[0][0]  # first prompt, first new token: [vocab_size]
probs = np.exp(logits - logits.max())
probs /= probs.sum()
assert tokenizer.decode([int(probs.argmax())]) == " Paris"

top = np.argsort(probs)[::-1][:10]
fig = go.Figure(
    go.Bar(
        x=probs[top],
        y=[repr(tokenizer.decode([int(i)])) for i in top],
        orientation="h",
        marker_color=viz.BLUE,
        text=[f"{p:.1%}" for p in probs[top]],
        textposition="outside",
        customdata=top,
        hovertemplate="%{y} (ID %{customdata}): %{x:.2%}<extra></extra>",
    )
)
fig.update_layout(
    title="The ten likeliest tokens after 'The capital of France is'",
    height=420,
    xaxis=dict(title="probability", tickformat=".0%", range=[0, 1.1]),
    yaxis=dict(autorange="reversed", showgrid=False),
)
viz.show(fig)

Generation repeats this step: pick a token from the distribution, append it, and run the model again. Picking the top token is greedy decoding; sampling from the distribution gives more varied text. Section 1.7 implements both.

Measure it

Two numbers describe how fast a model feels:

  • Time to first token (TTFT) is how long the user waits before anything appears. It covers prefill, which processes the whole prompt at once.
  • Time per output token (TPOT) is how long each later token takes. Each one is a decode step that processes a single new token.

Generating one token measures prefill; generating more adds decode steps.

def seconds(n_tokens: int) -> float:
    start = time.perf_counter()
    model.generate(
        input_ids=[ids], max_new_tokens=n_tokens, top_k=1, ignore_eos=True
    )
    return time.perf_counter() - start


ttft = seconds(1)
tpot = (seconds(65) - ttft) / 64
print(
    f"TTFT {ttft * 1000:.0f} ms, TPOT {tpot * 1000:.1f} ms ({1 / tpot:.0f} tokens/s)"
)

TTFT 16 ms, TPOT 9.1 ms (110 tokens/s)

On a timeline, one request is a prefill followed by a run of decode steps. The user waits through the prefill, then watches tokens arrive one decode step apart:

starts = [0.0] + [ttft + i * tpot for i in range(64)]
widths = [ttft] + [tpot] * 64
fig = go.Figure(
    go.Bar(
        x=np.array(widths) * 1000,
        base=np.array(starts) * 1000,
        y=["request"] * 65,
        orientation="h",
        marker=dict(
            color=[viz.ORANGE] + [viz.BLUE] * 64,
            line=dict(color=viz.SURFACE, width=1),
        ),
        customdata=["prefill (time to first token)"]
        + [f"decode step {i}" for i in range(1, 65)],
        hovertemplate="%{customdata}<br>starts at %{base:.0f} ms, takes %{x:.1f} ms<extra></extra>",
    )
)
fig.update_layout(
    title="One request: prefill (orange), then 64 decode steps (blue)",
    xaxis_title="milliseconds",
    height=220,
    margin=dict(t=56, b=48),
    yaxis=dict(showticklabels=False, showgrid=False),
)
viz.show(fig)

ignore_eos=True keeps generating past the end-of-sequence token, so every run does the same amount of work. LLM inference metrics in the handbook defines these and the other metrics engines report.

Close the pipeline to free its memory. max generate and max serve below load the model again.

pipe.close()

The command line: max generate

The max command, installed with MAX, runs the same pipeline from a shell. In a notebook, a line that starts with ! runs as a shell command. max generate applies the chat template to --prompt and prints timing statistics after the text.

!max generate --model HuggingFaceTB/SmolLM2-135M-Instruct --quantization-encoding float32 \
    --prompt "What is the capital of France?" --max-new-tokens 32 --top-k 1 2>/dev/null

The capital of France is Paris.

Output size: 8
Startup time: 0.3349781036376953 ms

Serve the model

max serve starts an HTTP server with an OpenAI-compatible API, so any OpenAI client library or tool can use your model. In a terminal you would run:

max serve --model HuggingFaceTB/SmolLM2-135M-Instruct \
  --quantization-encoding float32

From a notebook, start it in the background and wait until its /health endpoint answers:

server = subprocess.Popen(
    [
        "max",
        "serve",
        "--model",
        MODEL,
        "--port",
        "8000",
        "--quantization-encoding",
        "float32",
    ],
    stdout=subprocess.DEVNULL,
    stderr=subprocess.DEVNULL,
)
start = time.perf_counter()
while True:
    try:
        urllib.request.urlopen("http://localhost:8000/health")
        break
    except OSError:
        if server.poll() is not None:
            raise RuntimeError(
                "max serve exited; run it in a terminal to see why"
            )
        time.sleep(1)
print(f"server ready in {time.perf_counter() - start:.0f} s")

server ready in 16 s

Now call it with the official openai package. The API key is unused but required by the client.

client = OpenAI(base_url="http://localhost:8000/v1", api_key="unused")
reply = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "Name three primary colors."}],
    max_tokens=48,
    temperature=0,
)
print(reply.choices[0].message.content)
print(
    reply.usage.prompt_tokens,
    "prompt tokens,",
    reply.usage.completion_tokens,
    "completion tokens",
)
assert reply.choices[0].message.content.strip()

The primary colors are:

1. Red: A warm, reddish-brown color that is often associated with fire, blood, and fire.
2. Blue: A cool, deep, and deep blue color that is often associated with
35 prompt tokens, 48 completion tokens

Chat apps show the reply as it is generated. With stream=True the server sends each token as soon as the model produces it:

stream = client.chat.completions.create(
    model=MODEL,
    messages=[{"role": "user", "content": "Count from one to ten in words."}],
    max_tokens=48,
    temperature=0,
    stream=True,
)
for chunk in stream:
    print(chunk.choices[0].delta.content or "", end="", flush=True)

1. One
2. Two
3. Three
4. Four
5. Five
6. Six
7. Seven
8. Eight
9. Nine
10. Ten

server.terminate()
_ = server.wait()

What MAX did

Each call above ran the same pipeline:

text ─► tokenizer ─► token IDs ─► model ─► logits ─► sampler ─► next token
                                    ▲                                 │
                                    └──────── append and repeat ──────┘

Inside, MAX also compiled the model into optimized kernels, kept a KV cache so each decode step processes one token instead of the whole sequence, and scheduled requests so the server can batch them. In the rest of the book you build each of these parts yourself:
