1.8 The KV cache

Section 1.7 ended with a problem: each generated token reruns the model over the whole sequence, so the cost per token grows with the text. This section fixes it the way inference engines do, with a KV cache, and measures the difference.

Why caching works

To compute attention for a new token, the model needs the keys and values of every earlier position, in every layer. Those keys and values depend only on the tokens up to their own position, so they never change once computed. Recomputing them every step is wasted work. The KV cache stores them instead, which splits generation into two phases:

  • Prefill runs the whole prompt at once, like before, and saves every layer’s keys and values.
  • Decode runs one new token per step. Each layer computes the new token’s query, key, and value, appends the key and value to its cache, and attends over the whole cache.

The handbook’s How does LLM inference work? page describes the same two phases from the serving side.

    end = prompt_len + step
    recompute_work[step, :end] = 1
    cached_work[step, :end] = 1 if step == 0 else 0
    cached_work[step, end - 1] = 1

How big is the cache?

Each token stores one key and one value vector per key/value head, per layer. With \(L\) layers, \(H_{kv}\) key/value heads of dimension \(d\), and \(b\) bytes per number:

\[\text{bytes per token} = 2 \cdot L \cdot H_{kv} \cdot d \cdot b = 2 \cdot 30 \cdot 3 \cdot 64 \cdot 4\]

Even for SmolLM2 in float32, two sequences at the full 8,192-token context need a 720 MiB cache, more than the 513 MiB of weights. For large models serving many users, the cache often takes more GPU memory than the weights. The handbook’s GPU memory calculation adds it to the weights when sizing a deployment.

Attention with a cache

CachedAttention extends Section 1.5’s Attention. Its forward takes the layer’s cached keys and values, if any, and returns them extended by the new positions. start is the position of the first new token, so RoPE rotates the new queries and keys for where they really are.

Prefill uses the causal mask as before. Decode has one query, the newest token, which may attend to every cached position, so it needs no mask.

from __future__ import annotations

import math

import numpy as np
from max import functional as F
from max.driver import Device
from max.dtype import DType
from max.nn import ModuleList
from max.nn.kernels.attention import flash_attention
from max.tensor import Tensor
from max.tensor.tensor import TensorType

from minillm.attention import Attention
from minillm.config import LlamaConfig
from minillm.model import DecoderLayer, LlamaForCausalLM, LlamaModel

KVPair = tuple[Tensor, Tensor]


class CachedAttention(Attention):
    """Attention that reads and extends a key/value cache."""

    def forward(
        self, x: Tensor, start: Tensor, past: KVPair | None = None
    ) -> tuple[Tensor, KVPair]:
        q, k, v = self.project(x, start)
        if past is None:  # prefill: causal attention over the prompt
            return self.attend(q, k, v), (k, v)
        k = F.concat([past[0], k], axis=1)
        v = F.concat([past[1], v], axis=1)
        # The one new token may attend to every cached position: no mask.
        out = flash_attention(q, k, v, 1 / math.sqrt(self.head_dim))
        out = out.rebind_mapping(q.mapping)
        batch, seq = q.shape[0], q.shape[1]
        out = out.reshape([batch, seq, self.num_heads * self.head_dim])
        return self.o_proj(out), (k, v)

The layer and model pass each layer’s cache through. The model returns logits for the last position only: generation never needs the others, and skipping them saves most of the LM head’s work during prefill.

class CachedDecoderLayer(DecoderLayer):
    def __init__(self, config: LlamaConfig) -> None:
        super().__init__(config)
        self.self_attn = CachedAttention(config)

    def forward(
        self, x: Tensor, start: Tensor, past: KVPair | None = None
    ) -> tuple[Tensor, KVPair]:
        attn, kv = self.self_attn(self.input_layernorm(x), start, past)
        x = x + attn
        return x + self.mlp(self.post_attention_layernorm(x)), kv


class CachedLlamaModel(LlamaModel):
    def __init__(self, config: LlamaConfig) -> None:
        super().__init__(config)
        self.layers = ModuleList(
            [
                CachedDecoderLayer(config)
                for _ in range(config.num_hidden_layers)
            ]
        )

    def forward(
        self,
        input_ids: Tensor,
        start: Tensor,
        cache: list[KVPair] | None = None,
    ) -> tuple[Tensor, list[KVPair]]:
        x = self.embed_tokens(input_ids)
        new_cache = []
        for i, layer in enumerate(self.layers):
            x, kv = layer(x, start, None if cache is None else cache[i])
            new_cache.append(kv)
        return self.norm(x), new_cache


class CachedLlamaForCausalLM(LlamaForCausalLM):
    """Returns the last position's logits and the updated cache."""

    def __init__(self, config: LlamaConfig) -> None:
        super().__init__(config)
        self.model = CachedLlamaModel(config)

    def forward(
        self,
        input_ids: Tensor,
        start: Tensor,
        cache: list[KVPair] | None = None,
    ) -> tuple[Tensor, list[KVPair]]:
        hidden, new_cache = self.model(input_ids, start, cache)
        return self.lm_head(hidden[:, -1]), new_cache

Two compiled graphs

Prefill and decode have different inputs, so they compile into two graphs that share the same weights. The cache is a list of 30 (key, value) pairs. Its length, cache_len, is a named dimension, so one decode graph serves every step. start is a one-element tensor rather than a Python number, so that it is an input of the graph instead of a constant baked into it. It is float32 because RoPE computes its angles in float32, and float32 holds every position up to 2^24 exactly.

KVCacheDecoder keeps the cache between calls. It has the same interface as Section 1.7’s next_logits: given the tokens so far, it returns the next token’s logits, running a prefill for a new prompt and a decode step when exactly one token was added. It plugs straight into generate.

class KVCacheDecoder:
    """Returns next-token logits like a full forward pass, using a cache."""

    def __init__(
        self, model: CachedLlamaForCausalLM, config: LlamaConfig, device: Device
    ) -> None:
        self.device = device
        tokens = TensorType(DType.int64, ("batch", "seq_len"), device=device)
        one_token = TensorType(DType.int64, ("batch", 1), device=device)
        start = TensorType(DType.float32, [1], device=device)
        kv = TensorType(
            DType.float32,
            ("batch", "cache_len", config.num_key_value_heads, config.head_dim),
            device=device,
        )
        self.prefill = model.compile(tokens, start)
        self.decode = model.compile(
            one_token, start, [(kv, kv)] * config.num_hidden_layers
        )
        self.cache: list[KVPair] | None = None
        self.length = 0

    def __call__(self, ids: list[int]) -> Tensor:
        if self.cache is not None and len(ids) == self.length + 1:
            logits, self.cache = self.decode(
                self._tokens(ids[-1:]), self._position(self.length), self.cache
            )
        else:
            logits, self.cache = self.prefill(
                self._tokens(ids), self._position(0)
            )
        self.length = len(ids)
        return logits[0]

    def _tokens(self, ids: list[int]) -> Tensor:
        return Tensor(np.array([ids], dtype=np.int64), device=self.device)

    def _position(self, position: int) -> Tensor:
        return Tensor(
            np.array([position], dtype=np.float32), device=self.device
        )

Measure it

Time one decode step at several context lengths, with random prompts so that only the length matters:

def ms_per_token(next_logits, prompt: list[int], steps: int = 24) -> float:
    ids = list(prompt)
    ids.append(int(np.argmax(next_logits(ids).to_numpy())))  # prefill, untimed
    start = time.perf_counter()
    for _ in range(steps):
        ids.append(int(np.argmax(next_logits(ids).to_numpy())))
    return (time.perf_counter() - start) / steps * 1000

Hover over the points to read the timings; yours depend on your hardware and vary from run to run. Recompute grows with the context, because every step reruns attention over the whole sequence. The cached step grows much more slowly. Below a few hundred tokens the cache doesn’t pay off, and can even be slower, because fixed work, such as launching kernels and reading every weight, dominates a step of a model this small.

MAX’s own decode step is far faster: the TPOT measured in Section 1.1 was about 10 ms on the same machine. Part of the gap is this section’s simple design: every decode call passes the 60 cache tensors in and gets 60 new ones back, F.concat copies each layer’s whole cache into a new tensor, and the loop reads the logits back to NumPy to pick each token on the host. MAX’s engine writes new keys and values into preallocated cache blocks that its attention kernel reads in place, and it samples on the GPU. Section 5.3 builds a block-based cache and explains how production engines avoid the copy.

This simple cache has limits that production engines address:

  • Memory is allocated per sequence, as it grows. A server doesn’t know how long each reply will be, and contiguous per-sequence buffers fragment memory. Paged attention stores the cache in fixed-size blocks instead, like virtual memory pages.
  • It serves one sequence at a time. A decode step for one token barely uses the hardware. Engines batch many sequences per step, which needs a cache that holds sequences of different lengths.
  • Shared prompts are recomputed. Requests that start with the same system prompt could share those cache blocks (prefix caching).

Chapter 5 builds these into a small serving engine: Section 5.2 adds continuous batching, Section 5.3 a paged KV cache, and Section 5.4 prefix caching. The handbook covers each one: PagedAttention, batching, and prefix caching.
