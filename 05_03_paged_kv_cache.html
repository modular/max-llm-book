5.3 A paged KV cache

With continuous batching, memory limits how many requests can be in flight: every request needs room for its keys and values, and Section 1.8 measured 45 KiB per token for SmolLM2-135M in float32. The question is how to hand out that memory. A server doesn’t know how long a reply will be when it starts, so the simplest scheme reserves room for the maximum length, and most of that room goes unused. (ContiguousCache avoids the reservation by copying its arrays on every append, which costs time instead.) This section replaces the contiguous cache with a paged one, the idea behind vLLM’s PagedAttention and MAX Serve’s paged KV cache.

Blocks and block tables

Paging works like virtual memory. The cache memory is one pool of fixed-size blocks, each holding the keys and values of block_size tokens. A sequence owns a list of block numbers, its block table, and takes a new block from the pool only when its last block fills. A sequence’s blocks needn’t be next to each other, so free memory never breaks into gaps too small to use; the only waste is the unfilled part of each sequence’s last block. A finished sequence returns its blocks to the pool at once.

from __future__ import annotations

import numpy as np

from minillm.config import LlamaConfig


class BlockPool:
    """Fixed-size blocks of KV cache memory, shared by all sequences."""

    def __init__(
        self, config: LlamaConfig, num_blocks: int, block_size: int = 16
    ) -> None:
        self.block_size = block_size
        shape = (
            num_blocks,
            block_size,
            config.num_key_value_heads,
            config.head_dim,
        )
        self.keys = [
            np.zeros(shape, np.float32) for _ in range(config.num_hidden_layers)
        ]
        self.values = [
            np.zeros(shape, np.float32) for _ in range(config.num_hidden_layers)
        ]
        self.free = list(range(num_blocks))

    @property
    def num_blocks(self) -> int:
        return len(self.keys[0])

    def allocate(self) -> int:
        if not self.free:
            raise MemoryError("the KV cache pool is full")
        return self.free.pop()

    def available(self) -> int:
        """Returns how many blocks ``allocate`` can still hand out."""
        return len(self.free)

    def release(self, blocks: list[int]) -> None:
        self.free.extend(blocks)


class PagedCache:
    """One sequence's keys and values, stored in pool blocks."""

    def __init__(self, pool: BlockPool) -> None:
        self.pool = pool
        self.blocks: list[int] = []
        self.length = 0

    @property
    def num_layers(self) -> int:
        return len(self.pool.keys)

    def read(self, layer: int) -> tuple[np.ndarray, np.ndarray]:
        keys = self.pool.keys[layer][self.blocks].reshape(
            -1, *self.pool.keys[layer].shape[2:]
        )
        values = self.pool.values[layer][self.blocks].reshape(keys.shape)
        return keys[: self.length], values[: self.length]

    def append(self, layer: int, keys: np.ndarray, values: np.ndarray) -> None:
        size, start = self.pool.block_size, self.length
        if layer == 0:  # every layer stores the same positions
            while len(self.blocks) * size < start + len(keys):
                self.blocks.append(self.pool.allocate())
        for i in range(len(keys)):
            block, slot = self.blocks[(start + i) // size], (start + i) % size
            self.pool.keys[layer][block, slot] = keys[i]
            self.pool.values[layer][block, slot] = values[i]
        if layer == self.num_layers - 1:
            self.length += len(keys)

    def release(self) -> None:
        self.pool.release(self.blocks)
        self.blocks = []

read gathers a sequence’s blocks into one array for the step model. That copy keeps the code simple. Production engines skip it: their attention kernel reads the blocks in place through the block table, which takes a custom kernel like the ones Section 3.1 shows how to write. The engine needs three changes. It admits waiting requests in arrival order while the pool has blocks for their prompts. When a decode step needs new blocks and the pool is empty, it preempts the newest running request: it frees that request’s blocks and puts it back at the front of the queue, to recompute its prompt and the tokens it has generated so far when it runs again. And it returns a finished request’s blocks to the pool.

from minillm.engine import Engine
from minillm.step import Request


class PagedEngine(Engine):
    """An engine whose requests share one pool of KV cache blocks."""

    def __init__(self, *args, pool: BlockPool, **kwargs) -> None:
        super().__init__(*args, new_cache=lambda _: PagedCache(pool), **kwargs)
        self.pool = pool
        self.preemptions = 0

    def step(self) -> None:
        # Admit waiting requests in arrival order while their tokens so far fit.
        spare, admitted = self.pool.available(), 0
        for request in self.waiting:
            if self.blocks_needed(request) > spare:
                break
            spare -= self.blocks_needed(request)
            admitted += 1
        held = [self.waiting.pop() for _ in range(len(self.waiting) - admitted)]
        prefill = (
            self.waiting
            and len(self.running) < self.max_batch
            and (self.continuous or not self.running)
        )
        if not prefill and not self.running and held:
            raise MemoryError(
                "a waiting request needs more blocks than the pool has"
            )
        if not prefill:
            held = self.preempt_until_decode_fits() + held
        super().step()
        self.waiting.extend(held)

    def preempt_until_decode_fits(self) -> list[Request]:
        """Frees the newest requests' blocks until every running request can
        store its next token, and returns them to recompute later."""
        preempted = []
        while self.blocks_to_grow() > self.pool.available():
            if len(self.running) == 1:
                raise MemoryError(
                    "a request needs more blocks than the pool has"
                )
            request, cache = self.running.pop()
            cache.release()
            preempted.insert(0, request)
            self.preemptions += 1
        return preempted

    def blocks_to_grow(self) -> int:
        size = self.pool.block_size
        return sum(c.length + 1 > len(c.blocks) * size for _, c in self.running)

    def blocks_needed(self, request: Request) -> int:
        # A preempted request recomputes the tokens it already generated.
        tokens = len(request.prompt) + len(request.output)
        return -(-tokens // self.pool.block_size)

    def prefill_tokens(self, request: Request, cache: PagedCache) -> list[int]:
        return request.prompt + request.output

    def release_finished(self, batch: list) -> None:
        for request, cache in batch:
            if request.done:
                cache.release()

Paging only changes where the keys and values are stored. Serve the workload from Section 5.2 with a paged cache and compare the tokens:

def workload() -> list[Request]:
    now = time.perf_counter()
    return [

Blocks are handed out from wherever they are free, so a request’s blocks end up scattered across the pool, and a finished request’s blocks go straight to the next request. Only the block table records their order. This pool was big enough that no request was preempted; exercise 1 shrinks it until some are.

Why it matters: memory

Compare the memory each scheme ties up for a batch of four of these requests. A contiguous cache can’t grow in place, so when a request starts it must reserve room for the longest the request could get. That is SmolLM2’s full 8192-token context, or at best the request’s max_tokens limit, which API clients often set well above the length of the replies they get; the table below assumes 512. Paging allocates only what each sequence holds, rounded up to whole blocks of \(B\) tokens:

\[\text{blocks for } n \text{ tokens} = \left\lceil \frac{n}{B} \right\rceil\]

per_token = (
    2
    * config.num_hidden_layers
    * config.num_key_value_heads
    * config.head_dim
    * 4
)
batch = 4
actual = [len(r.prompt) + len(r.output) for r in paged_requests]
reserve_max_context = batch * config.max_position_embeddings
reserve_max_tokens = batch * (max(len(r.prompt) for r in paged_requests) + 512)
paged_tokens = sum(sorted(-(-n // 16) * 16 for n in actual)[-batch:])

print(f"{'scheme':38} {'tokens reserved':>15} {'memory':>9}")
for name, tokens in [

Saved memory becomes batch capacity. In the memory that one full-context reservation needs (8192 tokens), a paged cache fits about two hundred of these requests at roughly 40 tokens each, which is why most serving engines page their KV cache. The block size is a trade-off: bigger blocks waste more space in each sequence’s last block, and smaller ones mean longer block tables and more bookkeeping per step.

MAX Serve’s paged cache works the same way, and its attention kernels read the pages through the block table directly. Its scheduler also preempts a running request when the pool runs out of pages, and logs a warning that suggests giving the cache more memory. max serve exposes the settings. --kv-cache-page-size sets the block size, 128 tokens by default. --device-memory-utilization sets the fraction of device memory the process may use, 0.95 by default, and the KV cache pool gets what is left after the weights and other allocations. The pool size and --max-batch-size together limit how many requests run at once. The handbook’s PagedAttention page describes the algorithm, and GPU memory for LLMs shows how to size the pool.
