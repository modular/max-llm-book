7.3 Structured output and tools

A chat answer is for people. A program needs output it can parse: a JSON object with the right fields, or the name of a function to call with its arguments. Instructions in the prompt don’t get that reliably, least of all from a small model. This section makes the server guarantee the format with structured output, then builds function calling on top of it.

import json

def chat(messages: list[dict[str, str]], **options: object) -> str:
    completion = client.chat.completions.create(
        model=MODEL_ID,
        messages=messages,
        max_tokens=100,
        temperature=0,
        **options,
    )
    return completion.choices[0].message.content

Describe the answer you want as a Pydantic model instead. Pydantic turns it into a JSON schema, which the request passes as response_format:

class City(BaseModel):
    model_config = ConfigDict(extra="forbid")  # no fields beyond these
    name: str
    country: str
    landmarks: list[str] = Field(min_length=3, max_length=3)


schema = {
    "type": "json_schema",
    "json_schema": {"name": "City", "schema": City.model_json_schema()},
}
answer = chat(question, response_format=schema)
print(answer)
city = City.model_validate_json(answer)
city

{"name":"Rome","country":"Italy","landmarks":["The Colosseum","The Roman Forum","The Pantheon"]}
City(name='Rome', country='Italy', landmarks=['The Colosseum', 'The Roman Forum', 'The Pantheon'])

model_validate_json raises if the text doesn’t match the schema. With structured output, the text always matches.

How the server guarantees it

The guarantee comes from the sampler. MAX compiles the schema into a grammar, and at every decode step the grammar says which tokens may come next: after {"name": "Rome", , only tokens that continue toward "country". MAX masks every other token out of the logits before sampling, as the top-p filter in Section 1.7 did with \(-\infty\), so the model can only pick a token that keeps the output valid. Generation ends when the grammar is complete.

The schema fixes the form of the answer and leaves the facts to the model. The model can skip any requirement that the schema leaves out: without min_length, a small model may return an empty landmarks list. Put every requirement you can into the schema, and check the values that matter. The handbook’s structured outputs page covers schema design and the cost of constrained decoding.

Function calling

A tool is a function that the model may ask your program to run: look up the weather, query a database, call an API. The model never runs anything itself. It writes the function’s name and arguments, your code runs the function, and the result goes back into the conversation. A tool call is therefore a structured output whose schema is “one of these functions, with valid arguments for it”.

Here are two tools, each a Python function plus a schema for its arguments:

RATES = {"USD": 1.0, "EUR": 0.92, "JPY": 151.0}


def get_weather(city: str) -> dict[str, object]:
    return {
        "city": city,
        "temperature_c": 18,
        "sky": "light rain",
    }  # a stand-in for a weather API


def convert_currency(
    amount: float, source: str, target: str
) -> dict[str, object]:
    return {
        "amount": round(amount / RATES[source] * RATES[target], 2),
        "currency": target,
    }


def arguments(**properties: dict[str, object]) -> dict[str, object]:
    return {
        "type": "object",
        "properties": properties,
        "required": list(properties),
        "additionalProperties": False,
    }


TOOLS = {
    "get_weather": (
        get_weather,
        "Gets the current weather in a city.",
        arguments(city={"type": "string"}),
    ),
    "convert_currency": (
        convert_currency,
        "Converts an amount between currencies.",
        arguments(
            amount={"type": "number"},
            source={"enum": list(RATES)},
            target={"enum": list(RATES)},
        ),
    ),
}

The schema for a call allows any one of the tools: anyOf lists one object per tool, each with its fixed name and its own arguments. enum limits the currencies to the ones RATES knows, so the model can’t ask for one the function would fail on. The system prompt tells the model what the tools do:

call_schema = {
    "anyOf": [
        {
            "type": "object",
            "properties": {"name": {"const": name}, "arguments": args},
            "required": ["name", "arguments"],
            "additionalProperties": False,
        }
        for name, (_, _, args) in TOOLS.items()
    ]
}
system = (
    "You can call these functions. Reply with one call as JSON.\n"
    + "\n".join(
        f"- {name}: {description} Arguments: {json.dumps(args['properties'])}"
        for name, (_, description, args) in TOOLS.items()
    )
)


def call_tool(question: str) -> tuple[dict[str, object], dict[str, object]]:
    messages = [
        {"role": "system", "content": system},
        {"role": "user", "content": question},
    ]
    call = json.loads(
        chat(
            messages,
            response_format={
                "type": "json_schema",
                "json_schema": {"name": "call", "schema": call_schema},
            },
        )
    )
    function = TOOLS[call["name"]][0]
    return call, function(**call["arguments"])


for question in [
    "What's the weather in Tokyo?",
    "How much is 20 US dollars in euros?",
]:
    call, result = call_tool(question)
    print(f"{question}\n  call:   {call}\n  result: {result}")

What's the weather in Tokyo?
  call:   {'name': 'get_weather', 'arguments': {'city': 'Tokyo'}}
  result: {'city': 'Tokyo', 'temperature_c': 18, 'sky': 'light rain'}
How much is 20 US dollars in euros?
  call:   {'name': 'convert_currency', 'arguments': {'amount': 20, 'source': 'USD', 'target': 'EUR'}}
  result: {'amount': 18.4, 'currency': 'EUR'}

Every call parses and runs, since the grammar allows nothing else. Whether the model picks the right tool is up to the model; this one does on these questions.

The last step gives the result back so the model can answer. Here the result goes into the system prompt:

print("call:", call)

A 135M-parameter model uses the result loosely. Larger models follow it much more closely, especially ones trained for function calling.

Those models also take tools through the tools parameter of the OpenAI API. Their chat templates describe the tools to the model in the format it was trained on, and the model writes calls in its own format. MAX parses those calls with a tool parser for each model family, such as Llama, Qwen, and DeepSeek, and returns them as message.tool_calls; tool_choice="required" forces a call. SmolLM2’s chat template has no place for tools, which is why this section built the protocol by hand. The mechanism is the same in both cases: the model writes a structured call, and your code runs it. The handbook’s function calling page covers the API and the agent loops built on it.
